Evidence Engine

A local-first platform that carries a systematic review from research question to manuscript: PICO framing, per-database search design, AI-assisted title/abstract and full-text screening, citation snowballing, data extraction, PRISMA and risk-of-bias diagramming, multi-reviewer collaboration, and write-up, all running on the reviewer's own machine.

Deployment
Runs entirely on-device. No account, no hosted server, no telemetry.
Models
Local screening via Ollama, or cloud models (Anthropic, OpenAI, Google) with a key you supply.
Coverage
Ten open-access literature sources plus your own PDFs.

Evidence Engine is aimed at researchers running rigorous evidence syntheses who want AI to accelerate the mechanical work (query design, first-pass screening, extraction, drafting) without surrendering auditability or moving their data to someone else's cloud. It is intended as a transparent, self-hostable alternative to commercial review platforms.

This is the developer reference. It is regenerated whenever code is pushed, through the docs auto-update workflow, so it should track the current state of the app. If something here disagrees with the code, the code is right, please open an issue or run /sync-docs.

Design principles

Four commitments shape most decisions in the codebase. When a change is ambiguous, these break the tie.

1. Local-first, author-owned

There is no central service. The author's machine holds the data, and collaboration happens by exchanging bundles, not by connecting to a shared server. This keeps running cost near zero, makes privacy a property of the architecture rather than a policy, and lets anyone self-host by simply running the app.

2. Deterministic where it can be, AI where it must be

Anything that can be computed reproducibly is: deduplication, funnel counts, assignment splits, PRISMA rendering, and effect-size pooling are plain code with no model in the loop. The LLM is reserved for genuinely fuzzy judgments (relevance, extraction, drafting), and even there its output is captured as data that a human can override.

3. AI as an accelerator, not an oracle

Every AI decision is recorded alongside a human-visible rationale and can be overridden; overrides are audit-logged. In multi-reviewer mode the AI is one voice, not the arbiter, conflicts resolve through human adjudication.

4. Transparency by default

The Writing Assistant emits an explicit AI-disclosure statement and a full search appendix (strings, dates, per-database counts) to meet PRISMA and RAISE/Cochrane reporting expectations. The goal is that a reader can reconstruct exactly what was searched, screened, and generated.

The frontend never imports backend code; it talks only through apiFetch() in src/app/lib/backendClient.ts, which issues /api/* calls that Vite proxies to localhost:8000. Two FastAPI routers are mounted under /api: the review pipeline (Backend/api.py) and the projects/sessions store (Backend/store.py).

Request lifecycle

A representative call, screening one abstract, illustrates the path every request takes.

  1. The page calls apiFetch("/screen/abstract", { method: "POST", body }). The client attaches the X-Reviewer-Id header identifying the active local profile.
  2. Vite proxies /api/screen/abstract to the FastAPI backend on port 8000.
  3. FastAPI validates the body against a Pydantic model and resolves the model to use (request field, else DEFAULT_MODEL).
  4. The backend builds a per-PICO prompt and invokes the model (local Ollama or a cloud provider). Long or batched work is dispatched through a bounded thread pool (PARALLEL_SCREENING_WORKERS, default 16) and tracked as a cancellable task.
  5. The judgment (decision, rationale, per-criterion verdict) is returned as JSON. In a project context it is also persisted to the store as a decision record.
  6. The page updates review state and mirrors the session to IndexedDB so a reload restores it.

Long-running operations (agentic search, batch screening) expose progress and can be cancelled through POST /api/tasks/cancel and POST /api/tasks/cancel-all. One endpoint, POST /api/simulation/agentic/stream, streams incremental results back to the UI.

Quickstart

For reviewers

  1. Download and unzip a release, then double-click Evidence Engine.app (macOS) or run launch.command / launch.bat.
  2. On first run the launcher provisions an isolated Python environment, installs and starts Ollama, and pulls the default screening model. This is a one-time cost.
  3. The window opens at localhost:5180. Choose a model in the sidebar (local needs nothing; cloud needs a key in your environment).
  4. Begin on Research Strategy, frame a PICO question, and work down the pipeline.
  5. Close the app window to shut the entire stack down.

For developers

git clone <repo> && cd "Systematic Review Platform"
git config core.hooksPath .githooks   # enable the docs-freshness gate
pnpm install                          # frontend deps
node launch.mjs                       # run the full stack like a user would

The review pipeline

Each sidebar entry is a stage. They are ordered to match the arc of a review, but state is shared across the whole app, so you can move between them freely and revisit earlier stages as the corpus changes.

Research Strategy→ Search Planning→ Quality Assessment→ Abstract Screening→ Full-Text Acquisition→ Full-Text Evidence→ Snowballing→ Extraction→ Diagramming→ Writing

Meta-analysis exists as a stage but is hidden in the current navigation. The sections below document each stage in the order above, with what it does and how it works.

Screening model

Screening is where the AI does its most consequential work, so its mechanics matter.

Per-criterion judgments

Rather than asking "is this relevant?", the screener evaluates each paper against the PICO and the explicit inclusion/exclusion criteria and returns a structured verdict: an overall include / exclude / maybe, a natural-language reason, and a per-criterion breakdown. Excluded records are bucketed by the failing criterion so the PRISMA diagram can report reasons for exclusion.

Two passes

Abstract screening works from title and abstract with high throughput. Full-text evidence re-evaluates the acquired full text against each inclusion criterion, a stricter gate that produces the final included set.

Concurrency

Batch screening runs through a bounded thread pool sized by PARALLEL_SCREENING_WORKERS (default 16). Local models are typically run at lower effective concurrency than cloud models because a single machine's GPU is the bottleneck.

Human authority

Every AI decision is overridable. An override is stored as a decision with is_override = true and is preserved through later stages (snowballing and extraction honor reviewer overrides on the seed set). In multi-reviewer projects the cached AI decision is only a fallback, used when no human has decided a paper yet (see Conflicts & adjudication).

Data & privacy

Because there is no server, user data stays on the user's disk by default. The store is a SQLite file at ~/.evidence-engine/evidence.db. The app collects no telemetry.

The one exfiltration path is the cloud model option. Selecting a cloud model (Anthropic, OpenAI, Google) transmits paper titles, abstracts, and full text to that provider for the duration of the call. For sensitive or unpublished reviews, use a local Ollama model, which keeps everything on-device. A local-only mode that hard-disables cloud providers is on the roadmap.

Systematic reviews operate on published literature, so in typical use no patient-level or otherwise regulated data is involved. If a user chooses to load private data, it remains local unless they explicitly select a cloud model.

Research Strategy

Page home · PICO-driven question framing and search design.

The entry point. A plain-language research question is turned into a structured PICO (Population, Intervention, Comparator, Outcome), optionally refined through clarifying questions and adversarial critique, and then compiled into a canonical PubMed-style Boolean query with synonym and MeSH expansion. That canonical query is the single source of truth the rest of the pipeline adapts per database.

How it works

  1. The question goes to /api/pico/infer, which returns a structured PICO with candidate terms for each facet.
  2. Optional refinement loops sharpen it: clarify-questions and clarify-next resolve ambiguous facets through a short dialogue, adversarial critiques the framing for scope errors, and brainstorm / suggestions expand synonyms.
  3. formal-question composes the written review question. The PICO is then compiled into a Boolean query where each facet becomes an OR-group of synonyms plus MeSH terms, and the facets are joined with AND.
  4. The canonical query and PICO are held in session state and mirrored to IndexedDB, so every later stage reads the same definition.

Inputs: a plain-language question. Outputs: a PICO object, a formal question, and the canonical Boolean query.

Key endpoints: /api/pico/infer, /api/pico/clarify-questions, /api/pico/clarify-next, /api/pico/formal-question, /api/pico/refine, /api/pico/adversarial, /api/pico/suggestions, /api/pico/brainstorm, /api/pico/summary.

Search Planning

Page simulation · Per-database query tuning with agentic optimization.

Estimates yield per source and runs an agentic optimizer that rewrites the query into each database's native syntax, then broadens or narrows it across a ladder of deterministic tactics to find a good point on the retrieval-versus-relevance curve for that source. The result is a per-source query map used at fetch time, and a trace of what was tried.

How it works

  1. Yield estimate: /api/simulation/yield issues count-only queries to each source so you see how many records the current query would return before committing to a fetch.
  2. Syntax adaptation: the canonical PubMed query is translated per engine, PubMed keeps its [tiab]/[Mesh] tags; Europe PMC, OpenAlex, CrossRef, arXiv, DOAJ, and CORE keep quoted phrases and Boolean logic but drop the bracket tags; Semantic Scholar is flattened to a few keyword anchors because it does not honor Boolean operators.
  3. Tactic ladder: the agentic optimizer applies deterministic transformations, drop the population block, strip MeSH-only fragments, retag [tiab] to [ti], add wildcard variants, and measures the resulting count and relevance per source, keeping the best-performing variant. It stops a source when further tactics stop improving it.
  4. The streaming variant (/api/simulation/agentic/stream) reports each iteration to the UI as it runs.

Inputs: canonical query, PICO, active sources. Outputs: a per-source query map and an optimization trace.

Key endpoints: /api/simulation/yield, /api/simulation/adapt, /api/simulation/agentic, /api/simulation/agentic/stream.

Quality Assessment

Page quality · Deduplicate and surface issues in the acquired corpus.

Fetches records for the active query, deduplicates them, and flags problems (missing abstracts or metadata) before screening begins. This stage also surfaces appraisal instruments and hosts the risk-of-bias tooling that feeds the diagramming heatmap. Deduplication is deterministic and its counts flow into the PRISMA funnel.

How it works

  1. Fetch: /api/papers/fetch runs the per-source query map through fetch_all, returning records plus a per-source count. Deduplication is deliberately not applied at fetch time so the raw per-source totals are preserved for PRISMA.
  2. Dedupe: /api/papers/dedupe collapses duplicates deterministically (by normalized identifiers and title), and the number removed becomes the "duplicates" figure in the funnel.
  3. Triage: records missing abstracts or key metadata are flagged so you can decide whether to enrich or drop them before screening.
  4. Appraisal: /api/instruments lists risk-of-bias and quality instruments; /api/quality/assess and /api/grade run assessments whose results feed the diagramming heatmap and GRADE reporting.

Inputs: per-source query map. Outputs: a deduplicated corpus with funnel counts and quality flags.

Key endpoints: /api/papers/fetch, /api/papers/dedupe, /api/instruments, /api/quality/assess, /api/grade.

Abstract Screening

Page abstract · Title and abstract review.

Screens each title/abstract against the criteria using the per-PICO method described in the screening model, at bounded concurrency. Supports single-record and batch calls, reviewer overrides, and an optional relevance re-rank to surface the most likely includes first.

How it works

  1. For each record, the backend builds a prompt from the PICO and the inclusion/exclusion criteria and asks the model for a structured verdict: overall include/exclude/maybe, a reason, and a per-criterion breakdown.
  2. Batch calls (/api/screen/abstract-batch) dispatch records through a bounded thread pool (PARALLEL_SCREENING_WORKERS) and stream progress; the run is cancellable.
  3. Excluded records are bucketed by the criterion that failed, so the PRISMA funnel can report reasons for exclusion. An optional re-rank (/api/papers/rerank) orders the corpus by predicted relevance so likely includes are reviewed first.
  4. A reviewer can override any verdict; the override is stored with is_override = true and carried forward to acquisition and snowballing.

Inputs: deduplicated corpus, PICO, criteria. Outputs: per-paper decisions with reasons and exclusion buckets.

Key endpoints: /api/screen/abstract, /api/screen/abstract-batch, /api/papers/rerank.

Full-Text Acquisition

Page acquisition · Collect full text for included papers.

Retrieves open-access full text through structured Europe PMC / PMC content and the Unpaywall OA-PDF route, then caches the acquired PDF so the in-app reader works offline. A Reader / Raw / PDF tabbed view renders the text. Only open-access sources are used; there is no paywall circumvention.

How it works

  1. For each included paper, /api/fulltext/fetch tries structured Europe PMC / PMC content first (cleanest text), then falls back to the Unpaywall OA-PDF lookup keyed by DOI.
  2. A retrieved PDF is cached server-side and served back through GET /api/fulltext/pdf/{key}, which is what makes the PDF tab render without re-downloading.
  3. The reader exposes three views: Reader (clean text), Raw (unprocessed extract), and PDF (the original document).
Unpaywall rejects placeholder email addresses with HTTP 422, so a real ENTREZ_EMAIL is required for this stage. See Configuration.

Key endpoints: /api/fulltext/fetch, GET /api/fulltext/pdf/{key}.

Full-Text Evidence

Page fulltext · Per-criterion full-text evaluation.

Re-evaluates the acquired full text against each inclusion criterion, a stricter pass than the abstract stage, producing per-criterion judgments that determine the final included set and the last PRISMA exclusion bucket.

How it works

Where abstract screening works from a short summary, this stage feeds the acquired full text to the model and evaluates it against each inclusion criterion individually. Because the evidence is richer, borderline maybe calls from the abstract stage are resolved here, and exclusions carry the specific criterion that failed into the final PRISMA bucket. Only papers that pass every inclusion criterion enter the included set that drives extraction, diagramming, and the write-up.

Inputs: acquired full text for abstract-passed papers. Outputs: the final included set with per-criterion verdicts.

Key endpoint: /api/screen/fulltext.

Citation Snowballing

Page snowball · Backward and forward citation discovery.

Expands the corpus by following references (backward) and citing papers (forward) through Europe PMC, OpenAlex, and Semantic Scholar. Discovered records that arrive title-only have their abstracts back-filled (Europe PMC first, then OpenAlex) so downstream screening has text to work with. The seed set honors reviewer overrides from abstract screening.

How it works

  1. Each seed paper is resolved on a citation graph (Europe PMC, OpenAlex, or Semantic Scholar), then its references (backward) and citing papers (forward) are pulled through /api/citations.
  2. Citation lists often come back title-only, which would starve screening, so missing abstracts are back-filled: Europe PMC full-text search first, then OpenAlex, deduplicated by title and bounded by a cap.
  3. Newly discovered records re-enter the corpus and can be screened like any other paper, feeding back into the funnel shown above.

Inputs: the included/seed set (honoring overrides). Outputs: additional candidate records with abstracts.

Key endpoint: /api/citations.

Table & Text Extraction

Pages extraction, textextraction.

Table Extraction pulls tabular data from included papers, with a deterministic open-access PDF tier via pdfplumber before any model-based extraction. Text Extraction answers natural-language questions against a paper's text and pulls specific values (with units and time points), toggling between the PDF and the extracted text, with the PDF shown by default when you jump to a value.

How it works

  1. Tables: /api/extract/tables first tries a deterministic tier, pdfplumber over the open-access PDF, so cleanly structured tables are pulled without a model. It falls back to model-based extraction only when the deterministic tier does not find a usable table.
  2. Text values: /api/extract/text takes a natural-language question ("what was the primary outcome at 12 months?") and returns the value with its units and time point, grounded in the paper text. Locating a value switches the view to the source so you can verify it against the PDF.
  3. /api/pdf/metadata cleans titles, authors, year, and DOI from raw PDF text, used both here and when enhancing user-uploaded studies.

Inputs: included papers with full text or PDFs. Outputs: extracted tables and named values with provenance.

Key endpoints: /api/extract/tables, /api/extract/text, /api/pdf/metadata.

Diagramming

Page prisma · PRISMA flow, risk-of-bias heatmap, inter-rater reliability.

Three tabs. PRISMA flow renders the funnel from live counts (identified, deduplicated, screened, excluded by reason, included) with inline-editable values and aligned connectors. Risk-of-bias heatmap visualizes appraisal results across studies and domains. Inter-rater reliability reports agreement and kappa for multi-reviewer projects. The IRR tab is enabled only when a project is active.

How it works

The PRISMA counts are derived deterministically from the live corpus and the exclusion buckets recorded during screening, so the diagram always matches the actual funnel; any value can still be edited inline for edge cases the automation cannot know. The heatmap reads the risk-of-bias assessments stored per paper. Inter-rater reliability is computed from the multiple reviewer decisions on shared papers, reporting raw agreement and Cohen's kappa, which is why the tab requires an active project with more than one reviewer.

Meta-analysis

Page meta · Effect-size extraction and pooling. Currently hidden in navigation.

Extracts effect sizes from included studies and pools them under fixed- and random-effects models. The pooling math is deterministic (in Backend/meta_analysis.py); only the extraction step from unstructured text uses a model. The stage is implemented but hidden from the sidebar pending further validation.

Key endpoints: /api/meta/extract, /api/meta/pool, /api/meta/run.

Writing Assistant

Page writing · Methods summary, study table, citation export, grounded Q&A.

  • Methods write-up: generates a concise main-text Methods paragraph plus a detailed appendix (full search strings and a per-database table), grounded in the actual funnel. Returns { main_text, appendix, summary }.
  • Included-studies table: per-study design, population, intervention, comparator, and outcomes, exportable to Word.
  • Ask your evidence: grounded, cited question answering over the included corpus.
  • Citation export: BibTeX / RIS and a comprehensive search appendix with per-platform coverage.
  • AI disclosure: a transparent statement of where AI was used, for RAISE / Cochrane reporting.

Key endpoints: /api/writing/summary, /api/writing/characteristics, /api/writing/ask.

Projects & reviewers

Page projects · Multi-reviewer projects with blinded screening and adjudication.

A project is a shared review workspace: a corpus, a PICO, inclusion/exclusion criteria, a screening mode, and a set of reviewers. It turns the single-user pipeline into a coordinated multi-reviewer effort while keeping the author's copy authoritative.

Screening modes

ModeBehavior
singleOne user, AI as accelerator (the legacy single-user behavior).
dualTwo or more reviewers screen independently, unblinded. Faster, but reviewers can see each other's decisions.
dual_blindedEach reviewer sees only their own decision on a paper until they have decided it; the system then surfaces disagreements to the adjudicator. This is the Cochrane-style standard.

Roles

lead full control, defines reviewers and assignments. reviewer screens assigned papers. adjudicator resolves conflicts. viewer read-only. Roles are enforced on every project endpoint via a role check.

Members are user accounts that have joined via an invite; participants are author-defined reviewer slots (name, role, weight) used to plan the assignment split. There is no cap on either.

Assignment strategies

The lead-only Team & assignment workspace defines participants and splits the corpus across them. All strategies are deterministic (index rotation, no randomness), so re-running reproduces the same split. Papers flagged as calibration are held out of the split.

StrategyBehaviorExample (9 papers, 3 reviewers)
DualEvery paper screened by N reviewers, round-robin. N is capped at the reviewer count.N=2 → 6 / 6 / 6 slots
Overlap %Papers split one-per-reviewer for speed; a set percentage are double-screened as a QC check.33% → 3 / 6 / 3 slots
WeightedSingle reviewer per paper, distributed by participant weight using a largest-remainder split.weights 2:1:1 → 5 / 2 / 2
Manual / by-tagExplicit paper-to-reviewer assignment, optionally driven by tags.as specified

The workspace shows a per-reviewer count after assignment. These figures are verified against the live backend and match the algorithm in Backend/store.py. See Worked examples for the exact request/response.

Calibration & tags

Calibration set

Papers flagged as calibration are pulled out of the normal split and, by default, given to every reviewer along with a gold decision and a rationale. This lets a lead check whether a reviewer is calibrated against known-answer papers before trusting their other work, and gives new reviewers worked examples of the criteria in action.

Tags

A project carries a tag vocabulary, and each paper can carry tags. Tags organize the corpus and drive manual/by-tag assignment. Set the project vocabulary with PUT /api/projects/{pid}/tags and a paper's tags with PUT /api/projects/{pid}/papers/{paper_id}/tags.

Conflicts & adjudication

When reviewers disagree on a paper it becomes a conflict. In dual_blinded mode a reviewer cannot see others' decisions on a paper until they have decided it themselves, so conflicts are genuine independent disagreements, and they surface only to the adjudicator, lead, and viewers, never to reviewers still deciding.

Effective decision resolution

The client helper effectiveProjectDecision() resolves each paper's final state in a fixed precedence order:

  1. Adjudication if an adjudicator has ruled.
  2. Consensus if all reviewers who decided agree.
  3. Conflict pending if they disagree and no adjudication exists.
  4. AI fallback if no human has decided yet, using the cached AI decision.

Risk-of-bias assessments follow the same pattern, with their own conflict endpoint.

Key endpoints: /api/projects/{pid}/decisions, /api/projects/{pid}/conflicts, /api/projects/{pid}/adjudications, /api/projects/{pid}/rob-assessments, /api/projects/{pid}/rob-conflicts.

Federation model

With no server, reviewer work moves between machines as export/import bundles: the author defines the project and hands out papers, each reviewer screens locally, and their decisions return as a file that merges into the author's store. The author's copy is the source of truth. Invites (POST /api/projects/{pid}/invites, POST /api/invites/{token}/accept) model membership; a ?invite=TOKEN URL routes the app to the accept banner.

Implementation status. The collaboration data model, assignment, tagging, calibration, decisions, conflicts, adjudication, and risk-of-bias are built and tested. The bundle export/import that physically moves work between separate machines is the remaining piece to implement. Its format must be versioned (a version field plus a schema) before collaborators depend on it, so later changes do not break existing bundles.

Worked examples

Setting up a three-reviewer project and auto-assigning, the request/response shapes are exactly those verified against the running backend.

Create a project

curl -s -X POST localhost:8000/api/projects \
  -H 'content-type: application/json' \
  -H 'x-reviewer-id: alice' \
  -d '{"name":"Pet ownership and CVD"}'

Data store schema

Persistence is a single SQLite key-value table at ~/.evidence-engine/evidence.db (override with EE_DB_PATH), accessed through kv_get, kv_set, kv_get_by_prefix, and kv_del in Backend/store.py. Records are JSON values namespaced by key prefix, which lets prefix scans stand in for indexed queries.

Key patternHolds
reviewer:{uid}A local reviewer profile
session:{uid}:{sid}A saved review session for a user
project:{pid}Project record (PICO, criteria, mode, visibility, lock)
project_member:{pid}:{uid}Membership and role
user_project:{uid}:{pid}Reverse index: a user's projects
invite:{token}Invite token, role, expiry, usage
project_papers:{pid}The project corpus (list of papers)
project_participant:{pid}:{id}Author-defined reviewer slot (name, role, weight)
paper_assignment:{pid}:{paper}:{uid}One reviewer's assignment to one paper
project_tags:{pid}Tag vocabulary and per-paper tags
decision:{pid}:{stage}:{paper}:{uid}A reviewer's screening decision
adjudication:{pid}:{stage}:{paper}An adjudicator's final ruling
rob_assessment:{pid}:{paper}:{uid}A risk-of-bias assessment
There is no migration framework yet. Because these shapes will evolve, adding versioned migrations and a backup/export path is a priority before wider distribution, so a schema change never costs a user their review. Tracked on the roadmap.

The default local screener

The default, leads, runs a LEADS-native screening pipeline on a locally hosted 7B model. On the van_Dis_2020 benchmark it reports recall 1.000, specificity 0.676, MCC +0.260, and WSS@95 0.61, chosen so a fully local, private setup can screen with usable accuracy and no data leaving the machine. Cloud models are available for users who prefer them and accept the data-transfer tradeoff.

Data governance. Local models keep everything on-device. Cloud models transmit paper text to the provider. For sensitive or unpublished reviews, prefer the local path. See Data & privacy.

Desktop launcher

launch.mjs is a cross-platform Node script (wrapped by Evidence Engine.app, launch.command, and launch.bat). On launch it:

  1. Resolves ports (frontend 5180, backend 8000, shifting the backend if 8000 is taken by a foreign process).
  2. Provisions an isolated Python venv from Backend/requirements.txt.
  3. Installs and starts Ollama if needed, and pulls the default screening model.
  4. Serves the built frontend and starts the backend as detached process groups.
  5. Opens an app window in an isolated Chrome profile (~/.evidence-engine-appwin).
  6. Watches the window via a DevTools page check and tears the whole tree down when it closes.

Single-instance behavior uses a PID lock at ~/.evidence-engine/launcher.pid plus a live DevTools page check on the app window. A previous unclean exit can leave a stale lock or an orphaned Chrome process that makes a relaunch appear to "already be open"; recovery is documented under Troubleshooting, and hardening this path is on the roadmap.

Local dev setup

  1. Enable the docs hook once per clone: git config core.hooksPath .githooks.
  2. Install frontend deps: pnpm install.
  3. Create the backend venv from Backend/requirements.txt, and copy Backend/.env.example to Backend/.env.
  4. Run the full stack like a user: node launch.mjs. Or run pieces directly: pnpm dev (Vite on 5173/5180) and uvicorn for the backend on 8000.
  5. Before committing: pnpm typecheck and pnpm build.

Testing

Test coverage is currently thin, one backend test file (Backend/test_instruments.py) and no frontend tests, and expanding it is the highest-leverage quality investment. The natural first targets are the deterministic core, which is highly testable without touching a model or a network:

  • Backend (pytest): the assignment strategies in store.py, the KV helpers, query adaptation per source, and dedup.
  • Frontend (vitest): exclusionBucketing.ts, effectiveProjectDecision(), and the RIS/BibTeX/NBIB parsers.

Mock the external APIs and the LLM; test the platform's own logic, not the providers'. A CI workflow running typecheck, lint, tests, and build on every push is the mechanism that keeps this honest and is tracked on the roadmap.

Docs auto-update

The docs are a multi-page site generated from a single authored source, and kept current through a push-time, approve-each-edit workflow so they do not drift from the code.

How the site is built

You edit one file, docs/_source.html (the single page you would get by concatenating every section). Running node scripts/build-docs.mjs splits it into one page per section under docs/, sharing assets/docs.css, assets/docs.js, and the sidebar, and rewrites in-document links to point at the right page. Never hand-edit the generated *.html; they are overwritten on every build.

Keeping it in sync with the code

  1. Enable the hook once per clone: git config core.hooksPath .githooks.
  2. On git push, the pre-push hook compares the commits being pushed against the marker in docs/.docs-sync. If watched source (Backend/, src/app/, launch.mjs) changed but docs/ was not updated, it blocks the push and explains how to fix it.
  3. Run /sync-docs in Claude Code. It reads the diff since the marker (via scripts/docs-diff.mjs), proposes edits to docs/_source.html as normal approve-or-reject edits, then rebuilds the pages with scripts/build-docs.mjs. Nothing changes without your approval.
  4. Approve the edits; the marker advances (node scripts/docs-diff.mjs --commit). Commit docs/ and push again.

Emergency bypass (lets docs drift): git push --no-verify. Use sparingly.

Contributing

Contributions are welcome. Until dedicated governance files land (LICENSE, CONTRIBUTING, CODE_OF_CONDUCT, SECURITY, all on the roadmap), follow these working rules:

  • Keep the frontend and backend decoupled: the UI talks only through apiFetch, never imports backend code.
  • Prefer deterministic code over a model call whenever a result can be computed reproducibly.
  • Record every AI decision as overridable data, never as a silent side effect.
  • Run pnpm typecheck and pnpm build before opening a PR; add tests for pure logic you touch.
  • House writing style: plain and concise, no em-dashes.
  • If you change watched source, run /sync-docs so this reference stays accurate.

Troubleshooting

SymptomCause & fix
"Ollama isn't reachable"The launcher installs and starts Ollama automatically; if it does not clear, relaunch, or pick a cloud model in the sidebar. Confirm with ollama list.
Relaunch says "already open" but no window appearsA previous unclean exit left a stale lock or orphaned Chrome. Remove ~/.evidence-engine/launcher.pid and kill any process matching evidence-engine-appwin, then relaunch.
Full-text acquisition returns nothing / HTTP 422Unpaywall rejects placeholder emails. Set ENTREZ_EMAIL to a real address you control.
Semantic Scholar or CORE returns littleBoth rate-limit or gate anonymous traffic. Set SEMANTIC_SCHOLAR_KEY / CORE_API_KEY.
Slower performance from the app icon than the terminalEnsure a production build is served (pnpm build); the launcher serves the built bundle, not the dev server.
Attaching hundreds of PDFs feels slowParsing and screening are per-file. A soft warning appears past 500 PDFs; use smaller batches.
